## 第一部分 · 诊断：钱花在哪，为什么产出慢且差

### D1. 每个 agent 每轮都从零重建上下文（最大成本项）
- **实测**：一次 `rivet --goal` 运行的固定开销约 **24,500 input tokens**（含 22,784 cache-read）——因为每次都要把**完整 memory + 人设 + 环境**重灌一遍。
- **后果**：同一件事做 N 轮，就付 N 次这份固定成本。今天的账：**533 个文件 / 115 条消息 / 26 条给人类的汇报**，而真正的交付物只有 2~3 份。
- **结论**：**成本与"轮数"成正比，而不是与"成果"成正比** ✗ ← 这是"花钱如流水"的第一原因。

### D2. 没有任务状态机、没有去重键 → 同一件事反复做
- **实测**：同一个验收标准（YQC-10 的 DoD）被**重裁 v1 → v2**、月桥简报发到 **R14**、同一份包被多轮复核；`projects/` 里出现大量**同题多版**产出。
- **机制**：agent 开工前**不查"这件事是否已经做过、做到哪了"**；卡片只有标题，没有 `done_when / evidence / dedupe_key`。
- **结论**：**重复劳动没有被机制拦住** ✗（我只在规则层写了"同一件事只做一次"，**缺机制层**）。

### D3. 没有停止条件 → 无限自证
- **实测**：26 条人类汇报里，多数是"进度自证"而非"结果"；月桥的 standup 一度**每轮一条**。
- **机制**：任务没有"轮数/预算/时间上限"，也没有"什么时候必须收口"。
- **结论**：**agent 会把"继续讨论"当成工作** ✗。

### D4. 元工作吞噬产出
- **实测**：今天 533 个产出文件里，**417 个是"公共/月桥"目录**，其中相当部分是 app 代码审计副本（~18 MB 的 JS 副本）与简报；`某比赛交付项目`（真业务）382 个里也含 `_work/` 解包产物。
- **结论**：**大量算力花在"关于办公室自己"的事情上** ✗。

### D5. 串行 + 轮询 → 端到端慢
- **实测**：投递是"45 秒轮询 + 单次运行 10 分钟"；一个 agent 做完另一个才知道。
- **结论**：**并行度几乎没有** ✗，端到端时间 ≈ 串行求和。

### D6. 交付通道不可靠 → 重试放大成本（**已修**）
- **实测**：执行星域自己统计 `pty-submit 457 → delivered 113`，**盲打投递损耗 75%** ✗。
- **已修**：改用各引擎原生无头通道（`rivet --goal` / `dsh headless` / `codex exec` / `codebuddy -p`），收件箱可清零。

### D7. 结论：为什么"不如单 agent"
单 agent 一次读完上下文、一次做完、不写中间简报 ✓；而当前多 agent：**上下文重复付费 + 无去重 + 无停止条件 + 串行 + 元工作** ✗ —— 四条叠加必然更贵更慢 ✗✓。
**不是"多 agent 没用"，是"缺了让它省钱的四件机制"** ✓。

## 第三部分 · 还没做完 / 需要补测 / 需要做什么

### P0-1（阻塞一切实测）· F12：headless 员工"能读不能写"
- **现象**：DSH 现场复现 `sandbox-local windows-acl temp grant materialization failed and its cleanup also failed` → 读文件正常，跑命令即死（`exit 1`）。
- **影响**：**一切"要跑命令才有证据"的任务都做不了** ✗（包括本轮补测）。
- **需要做**：用 `diagnose-windows-sandbox-acl` 思路检查该路径及每一级父目录 ACL 并修复；或给 rivet 配 bash 白名单。
- **判据**：`tianshu-agent --goal "跑 ls 并报告"` 能跑完且产出文件；`hive/crashes` 不再新增该类错误。

### P0-2 · 任务状态机 + 去重键（机制层，替代 S1 的自觉）
- **需要做**：任务卡增加字段 `status / owner / done_when / evidence[] / dedupe_key / budget`；
  agent **开工前必须先查**：①同 `dedupe_key` 的卡是否已 done ②`projects/**` 是否已有同题产出 → 有则**只做增量**。
- **判据**：同一 `dedupe_key` 在账本里**只能有一条**产出记录；重复开工次数 = 0（可对 `log.jsonl` 统计）。

### P0-3 · 上下文瘦身（直接把 D1 的钱省下来）
- **需要做**：把"人设 + 记忆"压成**固定短前缀**（如 ≤2k tokens），其余按需检索加载（不是全量 memory）。
- **判据**：单次运行的 input tokens 从 ~24.5k 降到 ≤10k（用 `--json` 的 usage 字段实测）。

### P1-1 · 停止条件
- **需要做**：每任务设**轮数上限 + 预算上限 + 墙钟上限**，到点强制收口并交"完成/未完成 + 卡点"。
- **判据**：任何任务不会超过设定轮数；超限会自己停下并报告。

### P1-2 · 单 agent 对照基准（回答"到底值不值"）
- **需要做**：挑 3 个真实任务，各跑两遍：**单 agent 直跑** vs **多 agent 协同**；记录 tokens / 墙钟 / 交付物质量。
- **判据**：给出表格，多 agent 必须在**交付物质量或时间**上有可量化优势，否则就该缩减编制。

### P1-3 · 并行度
- **需要做**：无依赖的子任务并行分发（现在是 45s 轮询 + 串行）；同一轮里多个 agent 同时开工。
- **判据**：一个有 3 个独立子任务的任务，端到端时间 ≈ 单个子任务时间 × 1.3 以内。

### P2-1 · app 原生遥测（hook 桥）—— 未做
- **现象**：app 面板看不到这些引擎的思考/工具调用（它们不发 Claude 式 hook）。目前靠"终端 REPL + 流式渲染"替代。
- **需要做**：把 rivet/dsh 的事件翻译成 app 认的 hook。

### P2-2 · 月桥汇报进 app 界面 —— 未做
- 现象：它发了 26 条 `to:human`，但写在 `god\outbox\.sent\`，app 的「问我」板只收 `act=ask` → 界面不显示（现置顶到看板）。
- 需要做：改月桥规则用 `act=ask + needs_human`，或 app 侧读 god outbox。

### P2-3 · 外部额度（不可改代码）
- Codex：ChatGPT 额度锁（`try again at …`）；WorkBuddy：`429 额度已用尽`。

### 待补测的业务项（任务卡已投递，等 P0-1 修好才能真正跑）
- **T1**：`某比赛交付项目\` 的性能目标值实测（出卡耗时 / 离线命中率 / 包体增量）→ `验收报告-性能实测.md`
