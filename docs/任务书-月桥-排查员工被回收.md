## 九、追加症状（S6）：界面「没有实时终端」+ 全员显示空闲

**现象**：界面里点任何员工，终端页显示「该智能体没有实时终端」，状态一律「空闲」；
但**进程其实都活着**、并且**在正常工作**。

**反证（同一时刻采集）**：
- hive\log.jsonl：12:00:04 codex-mv2h4arh -> harness-mv3d0001（Codex 正常回件）
- hive\fleet.json：6 名 agent 全在，reaker: healthy，且 god.inboxBacklog = 1
- 进程：god/WorkBuddy/天枢三域 rivet+node 进程在跑；场景里能看到员工头顶冒
  「Reading a new message」气泡（说明 agent 层在工作）

**结论**：**app 的 UI 与这些 PTY 失去绑定**（终端面板拿不到 live PTY），
所以：① 终端看不到；② **在界面里发给员工的消息走终端注入这条路会丢**（月桥因此没收到人类交办的任务）。

**绕行（已验证有效）**：改用**收件箱文件**派活 ——
hive\agents\<agentId>\inbox\<id>.json（本任务书就是这样投给月桥的，inboxBacklog 变 1 且被读取）。
脚本：D:\徐\MunderDifflin\custom-cast\send_task_to_god.py（可改成发给任意 agent）。

**待查**：UI 与 PTY 的绑定在哪一步丢失（怀疑与 S4 的持久状态、或 restore 流程未在 UI 注册 PTY 有关）；
修好 S1–S6 后，界面终端、聊天式派活、员工状态才能恢复正常。

### S6 根因（已确诊并已修复）

**根因**：app 的**恢复流程（restore）不给 agent 分配 ptyId** ✗。界面的终端标签靠
gent.ptyId 绑定 PTY；ptyId 为空时就显示「该智能体没有实时终端」。
实测花名册：god 有 ptyId=pty-god ✓，其余 6 人全是 None ✗ —— 所以除月桥外所有员工都看不到终端，
而**界面里发给他们的消息又走「终端注入」** → 一并丢失。

**修复**（已生效，脚本 D:\徐\MunderDifflin\custom-cast\fix_ptyids.py）：
按 app 的规则 ptyId = "pty-" + agentId 给 6 人补齐（该规则与 app 自身日志里的

udging … on pty-tianshu-approve-mv3e02 一致）。补完后重启，花名册里的 ptyId **未被清掉** ✓，
右侧终端已出现 live · pty pty-god 的实时输出 ✓。

**给 Codex 的正式修法**：不要靠人工写花名册（会被 app 的持久状态覆盖/绕过），应在
**restore 流程里补上 PTY 注册与 ptyId 回写**，使恢复回来的员工与用『添加智能体』新建的员工
在终端、消息、遥测上完全等价。这是本次协同体验失效的直接原因。

### S7 根因（高度可疑，已做处置）：多员工共用同一工作目录 → 星域串台

**现象（人类反馈）**：点三个天枢星域的终端，**都显示同一个会话名（启明）**，而每个星域其实有各自不同的
系统提示词与名字（启明 / 天梁 / 瑶光 …）。人类判断：**app 分不清函数调用属于哪个星域**。

**机制**：app 把工具调用 / hook / 终端归属按 agentId + PTY + cwd 关联。恢复回来的 agent 里，**god、
天枢·执行、DSH 三人共用 D:\徐\agent** ✗，于是会话归属互相串台（终端的 live · pty 全部落向同一个会话）。

**处置（已执行）**：给每人分配独立工作目录，并把 .rivet（登录态）复制过去：
yueqiao / 	ianshu-exec / 	ianshu-approve / 	ianshu-fix / harness / codex / workbuddy
（脚本 D:\徐\MunderDifflin\custom-cast\split_cwds.py）。

**给 Codex 的正式修法**：restore 流程应为每个 agent 建立**独立会话记录**（agentId↔PTY↔cwd↔session 一一对应），
并在 hook 载荷里带上稳定的 agentId；不得依赖 cwd 去猜归属。修好后：终端各显示自己的星域名、遥测/工具瀑布归属正确、
「消息」页签能按员工分开看对话。
