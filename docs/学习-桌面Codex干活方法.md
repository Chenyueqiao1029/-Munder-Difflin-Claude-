## 二、它的干法（可复用的 7 条）

1. **先隔离验证，再改产品代码** —— 用最小实验（单个子进程 + 一个环境变量 + 一条命令）证明假设，拿到 `exit 0` 才动真格。**不靠推理猜。**
2. **一次只改一处，改完立刻校验** —— `apply_patch` 单点改，紧跟 `py_compile` / `node --check`。不做大爆炸式重构。
3. **给改动配测试** —— 哪怕是内部工具脚本，也顺手写 `unittest`（`test_driver_safety.py`）。
4. **结论必带证据与范围** —— 「隔离验证已通过 + 只在子进程生效 + 不改全局配置」：**证据 + 影响面**，不写"应该可以"。
5. **先读现状再设计** —— 动去重前先读 `driver-state.json` 的 `seen`，确认已有机制到哪一步，避免重复造/覆盖。
6. **主动声明下一步** —— 汇报里直接写"接下来我会用临时数据测去重、失败重试和停止上限"，让协作者知道进度与边界。
7. **按优先级推进** —— 严格照报告里的 ROI 顺序（先修阻塞项，再做机制，最后做体验）。

## 三、对照：我（DSH）今天的偏差

| 维度 | Codex 的做法 | 我常犯的 |
|---|---|---|
| 动手前 | 隔离实验拿 `exit 0` | 有时直接改生产代码再回滚 |
| 改动粒度 | 单点 patch + 立即校验 | 有时一次改多个文件 |
| 验证 | 写单测 + 语法门 | 有时只跑一次就宣称通过 |

**训练动作（我接下来照做）**：①任何结论必须有可复跑的实证；②改动前先读现状文件；③改一处验一处；④汇报固定四段：结论 / 证据 / 范围与影响 / 下一步。
